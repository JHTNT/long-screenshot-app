# 專案文件

本目錄保存 Android 長截圖 App 的產品、設計與驗收文件。每份文件只處理一個主題，避免主規格隨專案成長而失控。

目前基線以 `app/`、現有測試與近期 Git 歷史共同判定，不把規劃文件視為已完成清單。各文件會分開標示：

- **目前：** 程式碼中已有的行為；仍可能缺少實機驗收。
- **規劃：** 重要產品規則或尚未完成的驗收條件。
- **想法：** 只有明確保留的可能方向；不代表承諾。

## 文件地圖

檔名編號代表規格層次，由「做什麼」到「怎麼驗證」：

| 文件 | 主題 | 回答的問題 |
| --- | --- | --- |
| [01 產品規劃](01-product-plan.md) | 目前產品基線、產品規則、範圍與風險 | 現在做什麼、仍缺什麼 |
| [02 互動規格](02-interaction-design.md) | 現有畫面流程，以及尚待完成的互動要求 | 使用者現在看到什麼 |
| [03 實作計畫](03-implementation-plan.md) | 技術邊界、資料生命週期、目前進度與缺口 | 現在怎麼運作 |
| [04 拼接規格](04-stitching-spec.md) | 重疊、可信度、系統列、合成與降級的行為契約 | 核心演算法必須保證什麼 |
| [05 測試計畫](05-test-plan.md) | 現有自動測試與尚待執行的驗收計畫 | 已驗證與未驗證什麼 |

## 建議工作順序

1. 先讀[產品規劃](01-product-plan.md)，確認要做與不做的範圍。
2. 依[實作計畫](03-implementation-plan.md)了解目前程式責任邊界與已知缺口。
3. 修改個別功能時查閱[互動規格](02-interaction-design.md)與[拼接規格](04-stitching-spec.md)。
4. 以[測試計畫](05-test-plan.md)區分已通過的自動檢查與尚待執行的實機驗收。

## 後續擴充

只有重要決策需要改變且理由必須長期保留時，才新增 `decisions/` 文件；一般實作細節留在程式碼與測試中。
